# Pony Tesla 第一版产品需求

更新日期：2026-10-13（北京时间）

本文记录用户已选择的功能，以及落实这些功能的设计草案。产品范围确定不代表已验证车辆接口；涉及车辆能力的项目均须通过中国区接入和实车测试确认。

## 1. 定位与首个验证车型

- 面向中国大陆车主，以 iOS 为主。
- 首个验证车型为国产 2022 款 Model 3，非焕新版。
- 基础控车参考官方 App，重点增加逐次行程、历史轨迹和数据曲线。
- 后端负责持续采集、归档和计算；iOS 负责查看记录、交互和发送操作。

## 2. 功能范围决策

编号沿用前期讨论，便于后续增减。

| 模块 | 用户选择 | 第一版范围 |
| --- | --- | --- |
| A 车辆与快捷控制 | 全部保留 | A1–A8，并支持自定义首页显示的控制功能 |
| B 空调与舒适 | B1–B5 | 基础温控、加热、除霜、过热保护、宠物/露营、预约；不做 B6 多套温控预设 |
| C 行程 | 全部保留 | C1–C9；历史记录和积累数据以服务器为主存储，行程历史滚动保留 7 天 |
| D 充电 | 保留数据和操作，去掉费用 | 充电状态、控制、预约、记录、曲线和动画；不做费用、账单或省钱统计 |
| E 哨兵 | 只保留开关 | 状态显示与开启/关闭；不做停车分析、哨兵统计、视频或录像管理 |
| F 地图与导航 | 基础找车和搜点导航 | 车辆定位、基础找车、地点搜索、发送目的地；不做独立复杂路线规划 |
| G 车况与高级设置 | 支持的尽量完整 | G1–G8 按能力逐项实现，拆分子入口 |
| H 自动化与设置 | 预留后续扩展 | 第一版不提供通用规则编辑器；必要授权和数据管理仍需具备 |

## 3. 页面组织草案

### 原生实现与视觉要求（用户追加）

- 使用原生 SwiftUI，目标为 iOS 27 的系统 Liquid Glass 体验。
- 底部标签栏、导航栏、按钮、弹层、选择器与滑块优先使用系统组件。
- 字体使用系统字体和语义字号，支持 Dynamic Type、深浅色及系统辅助功能。
- 不沿用早期网页原型的字体和卡片控制风格。验收以 Xcode 构建和 iOS 原生运行结果为准。

建议采用四个底部入口，最终布局可在原型阶段调整：

1. **车辆**：车辆概览、自定义快捷控制，以及空调、找车、哨兵、车况入口。
2. **行程**：最近 7 天的行程列表、地图回放、曲线、汇总及导出。
3. **充电**：当前充电状态和动画、充电控制、预约、历史记录与曲线。
4. **我的**：账户与车辆授权、数据管理、应用设置。

G 的多个子入口统一放在“车辆 → 车况与设置”。H 暂不占用独立底部入口。

## 4. A：车辆首页与自定义控制

### 4.1 功能

| 编号 | 内容 | 说明 |
| --- | --- | --- |
| A1 | 电量、续航、在线状态 | 显示数据更新时间，区分在线、休眠、离线和缓存数据 |
| A2 | 锁车、解锁 | 显示命令执行结果 |
| A3 | 前备箱、后备箱 | 按硬件提供操作；不提供原厂硬件无法执行的前备箱自动关闭 |
| A4 | 车窗通风、关闭 | 按地区与车辆能力启用 |
| A5 | 鸣笛、闪灯 | 用于找车 |
| A6 | 远程允许驾驶 | 与蓝牙手机钥匙区分；不据此承诺替代官方手机钥匙 |
| A7 | 自定义快捷控制、手动组合操作 | 保留手动触发组合动作的范围；具体组合项待原型确定 |
| A8 | 本 App 操作记录 | 记录本应用发出的操作、时间和结果；不声称能获取所有官方 App 或车内操作 |

### 4.2 首页编辑

用户可以像使用官方 App 一样，自行选择哪些控制功能显示在首页，方便直接操作。

- 通过“编辑快捷控制”添加、移除及排序。
- 候选项来自本车辆支持的控制能力，包括锁车、行李箱、空调、充电、哨兵等。
- 未放入首页的功能仍可从完整功能页面访问。
- 修改后保存布局，重新进入 App 后保持；提供恢复默认布局。
- 操作过程中有发送中、成功和失败反馈，避免重复点击。
- 开关状态依据车辆回报更新，不能仅因按钮被点击就显示执行成功。
- 涉及解锁、打开行李箱和允许驾驶等操作，在交互设计中加入防误触措施。

A7 的手动组合与 H 的条件自动化分开：第一版可手动执行组合，不提供任意时间、地点、电量条件的规则引擎。组合中各动作分别呈现结果，不把部分成功显示为全部成功。

## 5. B：空调与舒适

保留 B1–B5：

- B1：温度显示、空调开关、温度设定。
- B2：车辆已配备且已开通的座椅、方向盘加热。
- B3：除霜、驾驶室过热保护。
- B4：宠物模式、露营模式。
- B5：预约出发与提前调温。

不纳入 B6 多套个人温控方案。原厂无对应硬件的控制不展示为可用，例如本验证车型不应仅因接口目录出现座椅冷却就显示通风按钮。

## 6. C：行程与服务器数据

### 6.1 功能

| 编号 | 内容 |
| --- | --- |
| C1 | 自动生成每段行程，展示服务器保留的最近 7 天历史 |
| C2 | 行程实际轨迹地图 |
| C3 | 起终点、开始/结束时间、里程、时长、平均速度等摘要 |
| C4 | 速度曲线，与地图位置联动 |
| C5 | 电量及功率曲线；功率依赖实车有效字段和计算验证 |
| C6 | 单次耗电、平均能耗及百公里能耗，标明计算口径和估算情况 |
| C7 | 时间轴回放，联动位置、速度、电量等信息 |
| C8 | 每日汇总与所保留行程之间的比较 |
| C9 | 行程标签、备注和导出 |

### 6.2 已确定的存储原则

- 行程历史及积累的轨迹、曲线、标签和备注保存在服务器端。
- iOS 本地缓存只用于体验优化，服务器是主要数据来源。
- 默认自动采集，不要求用户每次手动开始/结束，也不要求 App 始终在前台运行。
- 从成功接入并开始采集时积累历史，不承诺补回接入前 7 天的数据。
- 服务器保留最近 7 天行程历史，超期自动清理。

### 6.3 7 天保留的实施草案

以下为使开发可执行而采用的默认方案，保留期变化时需同步调整：

- 7 天按滚动 168 小时计算；存储采用 UTC 时间，界面按本地时区显示。
- 已完成行程以结束时间计龄，避免跨界行程在详情中只剩半条轨迹；行程内数据随该行程到期删除。
- 未结束行程及未归档样本单独设置过期与异常终止策略，避免异常行程无限留存。
- 服务端查询即时过滤已过期记录，清理任务负责删除底层数据。
- 相关轨迹、曲线、摘要、标签、备注、派生汇总和服务端临时导出文件一起遵守到期策略。
- 本地缓存同步失效；用户主动导出并保存到自己设备的文件由用户管理。
- 服务日志不重复保存完整轨迹；备份与恢复流程也需定义到期策略，恢复后不得重新暴露过期记录。

上述按行程结束时间计龄的方案，会使跨越保留边界的行程起始样本略早于 168 小时。若需要严格按每个采样点计龄，须改为截断轨迹并明确展示。

### 6.4 数据质量与行程划分

- 根据挡位、运动状态和位置等综合识别行程；不能在红灯停车时结束行程。
- 短暂停车的合并阈值通过实车采样确定。
- 断网、无效信号和数据缺口需要显式标记；地图不伪造未采集路段。
- 统一速度、里程、功率和能量单位，并记录计算方法。
- 电量百分比差不能直接作为精确耗电量。
- 功率、能耗及能量回收计算必须验证符号、采样间隔和可用字段；缺失时显示“数据不足”。

## 7. D：充电数据与动画

保留：

- 当前状态：是否插枪、是否充电、电量、目标上限、功率、预计剩余时间及可用的电压/电流。
- 基础操作：开始/停止、上限、电流、充电口、充电预约，按接口及车辆能力提供。
- 单次记录：开始/结束时间、时长、起止电量、充入电量、充电类型及可用的位置。
- 过程曲线：电量和功率随时间变化。
- 动画：充电、等待、暂停、完成、异常等状态的视觉反馈。

不做：费用、电价、账单、省钱统计；不设独立的充电站表现排名入口。

动画必须由真实充电状态驱动，离线或旧数据不能持续显示“正在实时充电”。支持系统减少动态效果设置。

充电历史和过程数据同样保存在服务器。用户本次明确了行程保留 7 天，未单独指定充电历史及 A8 操作日志的期限；第一版暂按 7 天设计为可调整的服务端策略，不视为已确认的独立长期保留需求。

## 8. E：哨兵开关

- 显示当前哨兵状态，并支持开启/关闭。
- 可加入首页自定义快捷控制。
- 显示执行失败、车辆限制或暂不可用等真实结果。

不纳入：停车历史、停车掉电、哨兵耗电统计、事件中心、实时视频、录像远程下载、导入和播放。C 的行程起终点仍然保留，但不扩展成停车分析产品。

## 9. F：基础地图与搜点导航

- 地图显示车辆最新位置及更新时间。
- 提供基础找车能力：定位车辆、结合手机位置提供前往车辆的路线入口；鸣笛/闪灯复用 A5。
- 搜索地点、选择目的地并发送到车机。
- 展示发送成功或失败，不能把“指令已发送”误称为“导航已开始”。

不纳入：多经停点规划、独立长途补能规划、独立历史停车地图及额外常用地点管理入口。

中国大陆地图服务、坐标转换、搜点与导航跳转方案在技术设计阶段确定。C2、C7 的行程轨迹与回放不受 F 简化影响。

## 10. G：车况与高级设置子入口

原则：尽量完整呈现实车支持的能力，但不因为接口有字段就把它显示为可用，也不把读取状态误当成可以修改设置。

| 子入口 | 覆盖项目 | 范围及限制 |
| --- | --- | --- |
| 轮胎与车况 | G1、部分 G2 | 四轮胎压、测量时间、可获得的车辆状态和告警；趋势依赖自己采集 |
| 电池与动力 | G2、G3 | 有效的电池/电机温度、电压、电流等；容量与衰减估算须独立验证，不能冒充官方检测 |
| 安全与驾驶 | G4、G5 | 限速、代客模式、行车 PIN 的受支持操作，按车主权限及状态限制处理 |
| 软件与更新 | G6、G7 | 软件版本、更新状态、可用发行说明、安排安装、取消尚未开始的倒计时 |
| 驾驶员与访问 | G8 | 读取驾驶员、邀请或移除访问，按官方权限边界处理 |

开发时维护车辆能力表：硬件不支持、权限不足、固件不支持、字段无效和暂时离线分别处理。敏感操作按实际 API 限制和防误触需求设计。

电池容量/衰减估算在 7 天数据窗口内若不足以可靠计算，应显示数据不足或暂不开放；不得为该功能自行扩大服务器历史保留期。

## 11. H：扩展预留与必要设置

- 预留自动化服务和设置入口的扩展位置，第一版不显示不可用的空白功能页。
- 不实现通用的时间、地点、电量规则编辑器或复杂自定义通知系统。
- 账户连接、车辆授权、断开连接、数据删除、导出及首页布局设置属于必要功能。
- B5、D 的官方预约功能和 A7 的手动组合操作仍在本期范围内。
- iOS 小组件、快捷指令及 Apple Watch 不作为本期必交付项，后续再确定。

## 12. 接入验证与验收重点

开发前先完成中国区开发者接入、车辆授权及钥匙配对，验证首辆车的固件和数据能力。接入验证需要用户自己的车辆授权，不能以界面原型代替实车验证。

核心验收：

1. 首页快捷控制可以选择、排序、持久化和恢复默认，操作有真实反馈。
2. 不打开 iOS App 时，服务端仍可在车辆与网络条件允许时接收行程数据。
3. 行程详情的地图与曲线使用同一时间轴，数据缺口和估算值有明确标识。
4. 服务器的 7 天到期查询和清理策略覆盖相关原始及派生数据。
5. 充电页面以数据和动画为主，不出现费用和账单功能。
6. 哨兵范围限于状态与开关；地图范围限于基础找车和搜点导航。
7. G 的子入口根据实际车辆能力显示，无效字段不以零值冒充正常数据。

实现顺序草案：车辆接入与遥测验证 → 页面原型 → 首页及基础控车 → 行程采集与回放 → 充电数据 → G 子入口完善。
